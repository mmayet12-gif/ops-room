How I set up Claude

Everything I build runs through one setup on one 2017 laptop. This is the user guide: nine layers, what each one does, exactly what I put in it, and what to copy first.

The nine layers

Think of it like onboarding a very fast new hire. First you tell them the house rules, then give them a team, then limit what they can sign off, then automate the checks. The last two layers are what make it get better on its own.

Layer by layer

01

Global instructions

One short file Claude reads in every project: ~/.claude/CLAUDE.md.

What's in mine
  • How to hand bulk, low-stakes work to my AI farm (free models first) instead of doing it inline.
  • What the farm is not for: code, money, legal, health, personal data.
  • A pointer to the token-saving tool (layer 7).
Copy this
  • Keep it under a page. It loads into every session, so every line costs you, every time.
  • Only put rules here that are true for all your projects.
  • Write it like a note to a new colleague, not a legal contract.

CA lensTone at the top. A few clear firm-wide rules beat a thick policy manual nobody reads.

02

Project rulebook (CLAUDE.md)

Each project has its own CLAUDE.md at the root. Mine is the "single source of truth" for that project.

The 8 house rules in my biggest project
  • Read this file and the design docs before changing anything.
  • Every AI call goes through one function, and it refuses paid endpoints.
  • Every job goes through one queue. Heavy jobs run only from midnight to 5 am, one at a time, and never when load shedding is due.
  • Only one component (the "Secretary") is allowed to message me. Everything else asks it.
  • Personal data stays in a folder that's never committed.
  • Every tool follows the same flow: architect spec, builder, tester, reviewer, merge. Nobody merges their own work.
  • "Done" means tests pass, docs, schedule, logging, error alerts, and 3 days of clean running.
  • When usage limits hit: stop cleanly, write a handover note with the exact next command, resume next window.
Copy this
  • Put a live status block at the top that Claude keeps updated. New sessions start informed.
  • Write a clear definition of done. It stops "it compiles, ship it".
  • Add the handover rule. Running out of usage mid-task stops being a disaster.
Starter template 
# CLAUDE.md - my-project
## Live status
- Working: ...  Next: ...
## Rules
1. Read docs/ before changing code.
2. Never commit data/ or .env.
3. Done = tests pass + README.
4. Out of usage? Write HANDOVER.md.

CA lensDocumented procedures plus a written definition of "complete". Same reason audit files have a standard index.

03

A team of subagents

Subagents are specialist roles in .claude/agents/. Each has one job, its own instructions and its own model size.

RoleJobModel
architectWrites the spec and acceptance tests before any code exists.Opus
reviewerSecurity and privacy review before merge: secrets, personal data, paid APIs, POPIA.Opus
builderImplements an approved spec in small commits on its own branch.Sonnet
testerRuns the tests against the spec and rejects anything failing.Sonnet
researcherChecks best practice, free API limits and terms before a build.Sonnet
secretaryDesigns everything that reaches me: the 06:00 brief, the 20:00 check-in.Sonnet
docsKeeps READMEs, changelog and the status block current.Haiku
opsWatches logs, restarts stuck work, opens issues for failures.Haiku
farm-dispatcherHands bulk work to the AI farm. Global, available in every project.Haiku
Copy this
  • Start with two: a builder and a reviewer. That alone catches a surprising amount.
  • Match model to judgment: biggest model for design and review, mid for building, smallest for housekeeping.
  • Write each description as "Use when ...". Claude picks the agent from that sentence.

CA lensSegregation of duties. The one who prepares never approves. A reviewer agent is maker-checker for code.

04

Permissions

Three lists in .claude/settings.json: what Claude can do alone, what needs my yes, and what it can never do.

Mine, in short
  • Allow: run tests and the linter, read git history, commit to a branch, read issues, list local models.
  • Ask: push, merge a PR, install packages, download new models.
  • Deny: read .env, read the personal data folder, rm -rf, force-push.
Copy this 
"permissions": {
  "allow": ["Bash(pytest:*)", "Bash(git status:*)",
            "Bash(git diff:*)", "Bash(git commit:*)"],
  "ask":   ["Bash(git push:*)", "Bash(pip install:*)"],
  "deny":  ["Read(./.env)", "Read(./data/**)",
            "Bash(rm -rf:*)", "Bash(git push --force:*)"]
}

CA lensDelegation of authority. Routine work is pre-approved, anything that leaves the building needs a signature, some things nobody can do.

05

Hooks

Small scripts that run automatically before or after Claude uses a tool. They don't rely on Claude remembering a rule.

My three
  • block-secrets (before any commit): stops the commit if a .env, database, key file or anything that looks like a password or token is staged.
  • post-edit-checks (after any Python edit): runs the linter and the fast test suite, and pushes the failure straight back to Claude.
  • rtk (before every shell command, global): rewrites commands so their output is compressed. See layer 7.
Copy this
  • If a rule really matters, make it a hook, not a sentence in CLAUDE.md. Instructions can be missed; a hook can't.
  • Exit code 2 blocks the action and shows Claude your message, so it fixes the cause.
  • Start with a secrets blocker. It's the cheapest insurance you'll ever buy.

CA lensAutomated preventive controls beat detective ones. Don't review for leaked passwords, make leaking one impossible.

06

Skills and plugins

A skill is a saved recipe (a folder with a SKILL.md) that Claude loads only when the task needs it. Plugins bundle skills, agents and hooks.

My project skills
  • new-tool-scaffold: folder, README, handler and tests for a new tool, already wired to the queue and the Secretary.
  • add-scheduled-job: the right schedule and the heavy/light flag.
  • add-data-importer: turns files I drop in into clean database rows, keeping the original.
  • add-telegram-command: a phone command or button for a tool.
Plugins and add-ons I use
  • caveman: makes Claude answer in short, clipped sentences. Fewer words out, same substance.
  • remotion-best-practices: for making videos in code.
  • Desktop app plugins: data analysis, design review, Desktop Commander, and browser control for posting and research.
Copy this
  • Any task you've explained to Claude three times becomes a skill.
  • Skills cost nothing until used: only the one-line description sits in context.

CA lensStandard working papers. Same template, same steps, every engagement. Quality stops depending on who's doing it that day.

07

AI farm and token savers

I'm on a normal subscription with no API bills. These are how I stretch it.

What works
  • RTK hook: compresses shell output before Claude reads it. Across 1,691 commands it saved 1.6M tokens, about 62%.
  • Right-sized models: Haiku for housekeeping, Opus only for design and review (layer 3).
  • The AI farm: any project drops a job in a folder; every 30 seconds the farm sends it to the cheapest brain that can do it. Local Ollama first, then Google Gemini's free tier, then Claude on the plan I already pay for. A junk answer (empty, cut off, refused) moves up a brain. Code and admin go straight to Claude. Jobs marked private never leave the laptop. Of 40 jobs so far, 12 were sent free-first and 9 stayed free.
  • Cache once: fetch data once, save it, let Claude read the file. My worst week had 96% of usage in one chat that kept re-fetching the same data.
  • Handover notes: a new session reads one page instead of re-discovering the project.

CA lensMateriality. Spend the expensive effort where being wrong is expensive.

08

Second brain and file structure

Plain Markdown files that hold what Claude should know about me, each project and every past decision. Each file has one job.

The map 
brain/                    # uploaded to a Claude Project
  00-about-me.md          who I am, how I work, how to work with me
  01-projects.md          what I'm building and why
  project instructions    "read these first; ask, don't guess"

~/.claude/
  CLAUDE.md               global rules, one page        (layer 1)
  agents/                 agents available everywhere   (layer 3)
  projects/<project>/memory/
    MEMORY.md             the index: one line per lesson
    <lesson>.md           one lesson per file           (layer 9)

<project>/
  CLAUDE.md               live status + house rules     (layer 2)
  docs/architecture.md    how the pieces fit
  docs/decisions.md       every decision, dated, with the why
  docs/HANDOVER.md        done, not done, exact next command
  docs/runbook.md         what to do when it breaks
  docs/specs/             one spec per tool, written before code
  .claude/                agents, skills, hooks, permissions
How the second brain works
  • Numbered files, read in order. 00 is the essentials and points to the rest.
  • The project instruction says: treat these files as the truth, never ask me to re-explain what's in them.
  • Gaps are marked [Add later: ...]. If one matters, Claude asks me instead of guessing.
Copy this
  • Write 00-about-me.md tonight: who you are, how you like to work, what you never want.
  • One fact, one place. If two files disagree, Claude will pick one, and not always the right one.
  • Keep indexes short. The index loads every time; the detail loads only when needed.

CA lensThe permanent file. Everything a new team member needs, in a standard order, so nobody starts from zero.

09

How it learns from itself

Every session leaves the next one smarter. Nothing here is magic: it's a habit of writing lessons down where the next session will read them.

  1. 1I correct something, or a fix teaches a lessontrigger
  2. 2Claude writes one memory file: the rule, why, and how to apply itrecord
  3. 3It adds one line to the MEMORY.md indexindex
  4. 4The next session loads the index and pulls the lesson when it's relevantrecall
  5. 5Now and then, merge duplicates and delete lessons that turned out wrongclean up
Lessons it has learned
  • Audit success rates, not just errors. Three times a feature died silently inside a caught error. Now it checks how often things succeed.
  • Optimise the input, not the output. Rank on what the platform measures, not on the number that comes out at the end.
  • Cache once. Fetch data once, save it, read the file.
Three more loops
  • Decisions log: 12 dated decisions with reasons in my biggest project, so settled questions stay settled.
  • Handover: each work window ends with the exact next command, so the next one starts running.
  • Results loop: my content pipeline scores what actually performed, re-ranks its plan towards the winners once a day, and orders more of them. Scores are recomputed from scratch each run, so a winner that fades loses its boost. Anything that needs a fact-check is parked for me, never auto-published.
Copy this
  • When you correct Claude, add: "remember this, and why". That one sentence turns a fix into a rule.
  • Save the why with every lesson. A rule without its reason gets applied in the wrong places.
  • Make any automatic learning auditable: log what it changed and why, and keep a human gate on anything public.

CA lensPost-implementation review and management letter points. Findings are written up, carried forward, and checked again next year.

Where it all starts

The master prompt

Every layer above came from one prompt I gave Claude Code on day one. It sets the mission, the cost rules, the team, the loops and the definition of done, then tells Claude to save itself as the project's CLAUDE.md. This is my version with the personal parts taken out. Fill in the <angle brackets> and it's yours.

Why it works
  • Roles, not tasks. Claude is the architect and operator. I approve and decide.
  • Hard limits up front: budget, hardware, hours, my 15 minutes a day.
  • It ends with questions. "Ask me at most 5, then build." No guessing, no endless interview.
Tips if you use it
  • Start with a short build list. Mine had 500 ideas and needed its own scoring script before anything got built.
  • Write 00-about-me.md first, so the very first session already knows who you are.
=== MASTER PROMPT: MY PERSONAL AI OPERATING SYSTEM ===

0. MISSION
You are the chief architect and operator of my personal AI system.
I work full-time. Timezone: <your timezone>. Goals: <save time, learn, grow an audience...>.
Budget: R0/month beyond my existing Claude plan. I spend at most 15 minutes a day on this.
You build, test, run, fix and improve everything. I approve, decide and supply data,
only through the Secretary (section 7).
Save this prompt as CLAUDE.md in the repo root and keep it updated as the single source of truth.

1. HARDWARE & COST RULES (<your laptop>, no GPU, always on)
- Claude Code BUILDS. Free local tools RUN things 24/7. Never call paid APIs.
- One heavy job at a time. Heavy work runs 00:00-05:00.
- Auto-start on boot, resume the queue after power cuts, pause heavy jobs before load shedding.
- Usage limits are real: batch build work, never retry blindly. If limits hit, stop cleanly,
  write a handover note, resume next window.

2. MODEL ROUTING
Build time: Opus for architecture, planning, hard debugging, security review.
            Sonnet for day-to-day coding (default). Haiku for docs, formatting, log triage.
Run time (local via Ollama): small model for tagging and routing, 7-8B for summaries and drafts.
All routing lives in one ask_llm(task_type, prompt) function. Benchmark speeds and record them.

3. SUBAGENTS (.claude/agents/, each with limited tools)
- architect (Opus): specs and acceptance tests before code.
- builder (Sonnet): implements specs in small commits.
- tester (Sonnet): writes and runs tests, rejects failures.
- reviewer (Opus): security, privacy, secrets, unsafe actions.
- ops (Haiku): monitors logs, restarts, fixes, tunes resources.
- docs (Haiku): READMEs, changelog, CLAUDE.md.
- researcher (Sonnet): checks best practice and APIs before each build.
- secretary (Sonnet): everything that needs me.
No subagent merges its own work: builder -> tester -> reviewer -> merge.
Create Skills for repeated procedures. Use hooks to run formatting/tests after edits
and to block commits that contain secrets.

4. GITHUB
- One private repo: /core, /tools/<tool> (own README + tests), /.claude, /docs
  (architecture, runbook, decisions log), /backlog.
- main = live, dev = integration, feature/<tool> per build. Conventional commits.
- NEVER commit personal data, tokens or .env. Data lives in /data (gitignored), backed up nightly.
- Issues = backlog and bug tracker; every failure opens an issue. Free CI runs tests on every push.

5. LOOPS & SCHEDULES
- Nightly build: top "todo" -> spec -> build -> test -> review -> merge -> morning report. Max 2 tools a night.
- Fix loop (every 4h): read logs and issues, fix what's safe, escalate the rest to the Secretary.
- Weekly: usage per tool, improve the top 3, propose killing unused ones.
- Monthly: results vs goals, reprioritise the backlog.
- 3 failures in a row: pause, open an issue, tell the Secretary.

6. CLAUDE ECOSYSTEM
- Claude Code builds; I check and approve from the Claude mobile app.
- Weekly "state of the system" summary goes into a Claude Project so my phone chats know my setup.
- Ask before adding any new connector or tool.

7. THE SECRETARY (my single point of contact)
- Only the Secretary may contact me. All tools send requests to its queue.
- Batching: 06:00 brief (max 3 quick taps), 20:00 check-in (max 10 min).
- Urgent exceptions only: security, deadlines within 24h.
- Every request states: what, why, minutes needed, deadline, default action if I don't reply.
- Remind once, again after 24h, then apply the default or park it. Never nag more than twice.
- Learn from me: if I ignore a request type, propose automating or dropping it.
- Weekly report: approved, waiting on me, done without me, my time spent.

8. SAFETY & PERMISSIONS
- Permissions allowlist in .claude/settings.json; never fully disable permission checks.
- Nothing posts publicly, emails externally or spends money without my approval.
- Respect privacy law and site terms; prefer APIs and RSS. Honest content only.

9. PLAN & DEFINITION OF DONE
Phase 0: core + GitHub + subagents + skills + hooks. Phase 1: the Secretary. Phase 2+: backlog.
The build list is a BACKLOG, not a to-do list. The architect scores every item on impact,
effort and resource cost; I approve the top items first.
Done = tests pass, README, schedule, logging, error alerts, and 3 days of successful running.
START: ask me at most 5 questions, then build Phase 0. Then send me a one-page setup checklist.

10. BUILD LIST
<your list of ideas, grouped by area. Mine started with 500.>
